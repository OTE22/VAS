# Shared runtime dependencies — everything that is identical on CPU and GPU.
#
# Included by BOTH requirements-cpu.txt and requirements-gpu.txt via `-r`.
# Add and remove packages HERE unless the package genuinely differs between
# the two hardware targets (that is only: the ONNX Runtime build and the FAISS
# build — see the two files that include this one).
#
# WHY THIS FILE EXISTS
# --------------------
# The CPU and GPU lists were standalone and 51 of their ~55 lines were
# byte-identical. They had already drifted: `sentence-transformers` and `tqdm`
# existed only on CPU, and `Pillow` was pinned on CPU but unpinned on GPU, so
# the same commit could ship two different Pillow majors. Inheritance removes
# the class of bug rather than the instances.
#
# NOTE ON REPRODUCIBILITY: most direct dependencies below carry no version, so
# resolving this file twice can produce two different environments from the
# same commit. A requirements-cpu.lock.txt intended to close that gap was
# DELETED because it had become actively harmful (nothing installed it; it was
# frozen from a container with pytest installed by hand; it carried a package
# removed from the list long before; and it was missing sqlglot, which broke 18
# sql_guard tests in a rebuilt container for no code reason).
#
# To reintroduce one, generate it from a CLEAN build (no INSTALL_DEV, no ad-hoc
# installs) and wire it into the Dockerfile in the same change:
#
#   docker compose -f docker/docker-compose.cpu.yml build --no-cache face_recognition
#   docker run --rm --entrypoint python face-detector/api:dev -m pip freeze > requirements-cpu.lock.txt
#   # then in Dockerfile.cpu:
#   #   pip install --no-cache-dir --no-deps -r requirements-cpu.lock.txt && pip check
#
# tests/test_compose_and_deployment.py::test_no_stale_lock_artifact enforces
# that: if a lock file exists, the build must install it, it must contain
# everything pinned here, and it must not carry development-only packages.

# ML dataset artefacts. backend/ml/dataset_builder.py writes training datasets
# as Parquet and trainer.py reads them back, both importing pyarrow directly.
# It used to arrive only as a transitive dependency of pandas — which nothing
# imports — so removing pandas silently broke ML training with
# "No module named 'pyarrow'". Declared where it is actually used.
#
# Pinned to the major actually verified in the image (2026-08-22): both the
# development and the regression images run pyarrow 25.0.1 on Python 3.11.16
# / numpy 1.26.4 / scikit-learn 1.9.0, and every registered Parquet dataset
# reads back with its full column set under it. An unpinned pyarrow beside a
# hard-pinned numpy==1.26.4 could silently change Parquet read-back in a
# future major; a new major is adopted by re-running that read-back proof.
# ---------------------------------------------------------------------------
pyarrow>=25.0.1,<26
